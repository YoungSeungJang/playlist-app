## 1. 프로젝트 개요

### 프로젝트 구조
- **Monorepo 구조** (Turborepo + pnpm)
- **apps/web**: React + Vite 프론트엔드
- **apps/api**: Express.js + Socket.io 백엔드
- **packages/shared**: 공통 타입 및 유틸리티

### 주요 기능
- 음악 검색 (Spotify API 연동)
- 실시간 플레이리스트 관리
- 사용자 인증 (Supabase)

---

## 2. 아키텍처 및 기술 스택

### 프론트엔드
- **호스팅**: AWS Amplify
- **이유**:
  - Git 연동 자동 배포
  - HTTPS 기본 제공
  - React/Vite 앱에 최적화
  - 빌드 및 배포 자동화

### 백엔드
- **호스팅**: AWS EC2 (Ubuntu)
- **프로세스 관리**: PM2
- **웹서버**: Nginx (리버스 프록시)
- **이유**:
  - Express.js + Socket.io 실시간 통신 필요
  - 더 많은 제어권 필요 (환경변수, 프로세스 관리)
  - Amplify는 정적 호스팅에 적합, 백엔드는 EC2가 더 적합

### 도메인 및 SSL
- **도메인**: DuckDNS (무료 동적 DNS 서비스)
- **SSL 인증서**: Let's Encrypt (무료)
- **도메인명**: playlist-api.duckdns.org

## 4. 상세 배포 과정

### 4.1 프론트엔드 배포 (AWS Amplify)

#### 초기 배포
- AWS Amplify 콘솔에서 GitHub 저장소 연동
- 빌드 설정:
  ```yaml
  version: 1
  frontend:
    phases:
      preBuild:
        commands:
          - npm install -g pnpm
          - pnpm install
      build:
        commands:
          - pnpm build --filter=web
    artifacts:
      baseDirectory: apps/web/dist
      files:
        - '**/*'
  ```
- 환경변수 설정 (초기):
  ```
  VITE_API_BASE_URL=http://localhost:3001
  ```

#### 첫 번째 문제 발견
- **증상**: 검색 기능이 작동하지 않음
- **원인**: localhost:3001로 하드코딩된 API URL
- **확인**: Amplify는 HTTPS로 배포되는데, localhost는 로컬 개발 환경용

### 4.2 백엔드 배포 (AWS EC2)

#### EC2 인스턴스 설정
1. **인스턴스 생성**
   - AMI: Ubuntu Server
   - 인스턴스 타입: t2.micro (프리티어)
   - 보안 그룹:
     - SSH (22): 내 IP
     - HTTP (80): 0.0.0.0/0
     - HTTPS (443): 0.0.0.0/0
     - Custom (3001): 0.0.0.0/0 (나중에 제거 권장)

2. **Node.js 환경 설정**
   ```bash
   # Node.js 18.x 설치
   curl -fsSL https://deb.nodesource.com/setup_18.x | sudo -E bash -
   sudo apt-get install -y nodejs

   # pnpm 설치
   npm install -g pnpm

   # PM2 설치 (프로세스 관리자)
   npm install -g pm2
   ```

3. **코드 배포**
   ```bash
   # Git clone
   git clone https://github.com/username/playlist-app.git
   cd playlist-app

   # 의존성 설치
   pnpm install

   # 빌드 (TypeScript → JavaScript)
   pnpm build
   ```

4. **환경변수 설정**
   ```bash
   # apps/api/.env 파일 생성
   PORT=3001
   NODE_ENV=production
   CLIENT_URL=https://main.d2wur1i1ypx7nc.amplifyapp.com
   SPOTIFY_CLIENT_ID=your_spotify_client_id
   SPOTIFY_CLIENT_SECRET=your_spotify_client_secret
   ```

#### PM2로 프로세스 시작

**첫 번째 시도 (실패)**:
```bash
cd ~
pm2 start playlist-app/apps/api/dist/apps/api/src/index.js --name playlist-api
```
- **문제**: .env 파일을 찾지 못함 (working directory 문제)
- **에러**: Spotify API "invalid_client" 오류

**해결 방법**:
```bash
# working directory를 apps/api로 설정
cd ~/playlist-app/apps/api
pm2 start dist/apps/api/src/index.js --name playlist-api
```
- PM2의 working directory가 중요 (.env 파일 위치 기준)
- **성공**: Spotify API 정상 작동

#### Nginx 리버스 프록시 설정

1. **Nginx 설치**
   ```bash
   sudo apt update
   sudo apt install nginx -y
   ```

2. **Nginx 설정 파일 생성**
   ```bash
   sudo nano /etc/nginx/sites-available/playlist-api
   ```

   ```nginx
   server {
       listen 80;
       server_name playlist-api.duckdns.org;

       location /api {
           proxy_pass http://localhost:3001/api;
           proxy_http_version 1.1;
           proxy_set_header Upgrade $http_upgrade;
           proxy_set_header Connection 'upgrade';
           proxy_set_header Host $host;
           proxy_set_header X-Real-IP $remote_addr;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
           proxy_set_header X-Forwarded-Proto $scheme;
           proxy_cache_bypass $http_upgrade;
       }

       location /health {
           proxy_pass http://localhost:3001/health;
       }

       location / {
           return 404;
       }
   }
   ```

3. **심볼릭 링크 생성 및 Nginx 재시작**
   ```bash
   sudo ln -s /etc/nginx/sites-available/playlist-api /etc/nginx/sites-enabled/
   sudo nginx -t  # 설정 테스트
   sudo systemctl restart nginx
   ```

#### DuckDNS 도메인 설정

1. **DuckDNS 가입 및 도메인 생성**
   - https://www.duckdns.org 접속
   - GitHub/Google 계정으로 로그인
   - 서브도메인 생성: `playlist-api`
   - EC2 퍼블릭 IP 입력: `3.37.55.243`

2. **도메인 확인**
   ```bash
   nslookup playlist-api.duckdns.org
   # 응답: 3.37.55.243
   ```

3. **HTTP 엔드포인트 테스트**
   ```bash
   curl http://playlist-api.duckdns.org/api
   curl http://playlist-api.duckdns.org/health
   # 정상 응답 확인
   ```

## 5. 발생한 문제와 해결 방법

### 문제 1: Mixed Content 에러

#### 증상
```
Mixed Content: The page at 'https://main.d2wur1i1ypx7nc.amplifyapp.com'
was loaded over HTTPS, but requested an insecure XMLHttpRequest endpoint
'http://playlist-api.duckdns.org/api/spotify/search'.
This request has been blocked; the content must be served over HTTPS.
```

#### 원인
- 프론트엔드: HTTPS (Amplify)
- 백엔드: HTTP (EC2)
- 브라우저 보안 정책: HTTPS 페이지에서 HTTP API 호출 차단

#### 해결 방법
백엔드에 SSL 인증서 설치하여 HTTPS로 변경

---

### 문제 2: SSL 인증서 발급 실패 (DNS SERVFAIL)

#### 첫 번째 시도: `--nginx` 모드
```bash
sudo certbot --nginx -d playlist-api.duckdns.org
```

**에러**:
```
Certbot failed to authenticate some domains (authenticator: nginx).
The Certificate Authority reported these problems:
  Domain: playlist-api.duckdns.org
  Type:   dns
  Detail: DNS problem: SERVFAIL looking up A for playlist-api.duckdns.org
```

**원인 분석**:
- Let's Encrypt 서버가 DuckDNS 도메인 조회 실패
- 로컬에서는 nslookup 정상 작동
- DNS 전파 시간 필요

#### 두 번째 시도: `--standalone` 모드
```bash
sudo certbot certonly --standalone -d playlist-api.duckdns.org
```

**에러**:
```
Could not bind TCP port 80 because it is already in use by another process
```

**원인**:
- Nginx가 80포트 사용 중
- Standalone 모드는 Certbot 자체 웹서버가 80포트 필요

**시도한 해결 방법**:
```bash
# Nginx 프로세스 강제 종료
sudo pkill nginx

# 80포트 확인
sudo lsof -i :80
# 결과: 여전히 Nginx 프로세스들이 실행 중

# systemctl 상태 확인
sudo systemctl status nginx
# 결과: failed 상태 (systemd와 실제 프로세스 불일치)
```

**실제 문제**:
- Nginx 프로세스가 좀비 상태로 남아있음
- systemd는 failed로 표시되지만 실제로는 실행 중

#### 최종 해결

**시간이 지난 후 재시도**:
```bash
# Nginx 상태 정리
sudo systemctl restart nginx

# --nginx 모드 재시도
sudo certbot --nginx -d playlist-api.duckdns.org -v
```

**성공!**:
```
Successfully received certificate.
Certificate is saved at: /etc/letsencrypt/live/playlist-api.duckdns.org/fullchain.pem
Key is saved at:         /etc/letsencrypt/live/playlist-api.duckdns.org/privkey.pem
This certificate expires on 2026-01-28.

Deploying certificate
Successfully deployed certificate for playlist-api.duckdns.org to /etc/nginx/sites-enabled/playlist-api
Redirecting all traffic on port 80 to ssl in /etc/nginx/sites-enabled/playlist-api

Congratulations! You have successfully enabled HTTPS on https://playlist-api.duckdns.org
```

**성공 이유**:
- DNS 전파 완료 (약 30분~1시간 소요)
- DuckDNS 서버가 안정화됨
- Let's Encrypt가 도메인 조회 성공

**Certbot이 자동으로 처리한 것들**:
1. Nginx 설정에 SSL 인증서 경로 추가
2. 443포트 설정 추가
3. HTTP(80) → HTTPS(443) 자동 리다이렉트
4. 인증서 자동 갱신 스케줄 등록

### 문제 3: CORS 에러

#### 증상
```
Access to fetch at 'https://playlist-api.duckdns.org/api/spotify/search?q=bts'
from origin 'https://main.d2wur1i1ypx7nc.amplifyapp.com'
has been blocked by CORS policy:
The 'Access-Control-Allow-Origin' header has a value
'https://main.d2wur1i1ypx7nc.amplifyapp.com/'
that is not equal to the supplied origin.
```

#### 원인
- 백엔드 CORS 설정: `https://main.d2wur1i1ypx7nc.amplifyapp.com/` (끝에 `/`)
- 실제 브라우저 Origin: `https://main.d2wur1i1ypx7nc.amplifyapp.com` (끝에 `/` 없음)
- CORS는 정확한 문자열 매칭 → trailing slash 차이로 인한 불일치

#### 해결 방법
```bash
# .env 파일 수정
nano ~/playlist-app/apps/api/.env

# 변경 전
CLIENT_URL=https://main.d2wur1i1ypx7nc.amplifyapp.com/

# 변경 후
CLIENT_URL=https://main.d2wur1i1ypx7nc.amplifyapp.com

# PM2 재시작
pm2 restart playlist-api
```

**주의사항**:
- `.env` 파일만 수정 시 빌드 불필요
- PM2 재시작만으로 새 환경변수 적용됨
- PM2 restart는 어디서든 실행 가능 (working directory 유지)

### 문제 4: 환경변수 경로 문제

#### 증상
```
https://54.123.45.67:3001/api/spotify/search?q=bts
net::ERR_CONNECTION_TIMED_OUT
```

#### 원인
- Amplify 환경변수가 EC2 IP 주소로 설정됨: `https://54.123.45.67:3001`
- 포트 3001 포함 (외부에서 접근 불필요)
- DuckDNS 도메인 사용 안 함

#### 해결 방법

**Amplify 환경변수 수정**:
```
# 잘못된 설정
VITE_API_BASE_URL=https://54.123.45.67:3001

# 올바른 설정
VITE_API_BASE_URL=https://playlist-api.duckdns.org/api/spotify
```

**이유**:
1. 포트 번호 불필요
   - HTTPS 기본 포트: 443
   - Nginx가 443에서 수신 → 내부적으로 3001로 프록시

2. 도메인 사용 필수
   - SSL 인증서가 도메인(playlist-api.duckdns.org)용으로 발급됨
   - IP 주소로 접근 시 인증서 검증 실패

3. 전체 경로 포함
   - `musicApi.ts`에서 `API_BASE_URL`이 `/api/spotify` 경로 포함
   - 환경변수도 전체 경로 포함해야 함

### 문제 5: TypeScript ES Module 에러 (과거 문제)

#### 증상
```
Error [ERR_UNSUPPORTED_DIR_IMPORT]: Directory import
'.../@/config' is not supported resolving ES modules
```

#### 원인
- TypeScript의 path aliases (`@/`, `@shared/`)가 런타임에 해석 안 됨
- ES Module vs CommonJS 충돌

#### 해결 방법 (당시 적용)
1. tsconfig.json 변경
   ```json
   {
     "compilerOptions": {
       "module": "CommonJS",
       "moduleResolution": "node"
     }
   }
   ```

2. package.json에서 `"type": "module"` 제거

3. Path aliases를 상대 경로로 변경
   ```typescript
   // 변경 전
   import { spotifyConfig } from '@/config/spotify'
   import type { SimpleTrack } from 'shared'

   // 변경 후
   import { spotifyConfig } from '../config/spotify'
   import type { SimpleTrack } from '../../../../packages/shared/src/types/music'
   ```

## 6. 배포 완료 및 테스트

### 최종 아키텍처

```
사용자 (브라우저)
    ↓ HTTPS
[AWS Amplify - React App]
    ↓ HTTPS
    ↓ https://playlist-api.duckdns.org/api/spotify/search
    ↓
[Nginx - SSL 종료, 리버스 프록시]
    ↓ HTTP (localhost:3001)
[PM2 - 프로세스 관리]
    ↓
[Express.js - 백엔드 API]
    ↓
[Spotify API]
```

### 포트 구조
- **80 (HTTP)**: Nginx → HTTPS로 리다이렉트
- **443 (HTTPS)**: Nginx → SSL 처리 → localhost:3001로 프록시
- **3001 (HTTP)**: Express.js 백엔드 (내부 통신만)

### 보안 그룹 설정
```
Type        Protocol   Port Range   Source
SSH         TCP        22           내 IP
HTTP        TCP        80           0.0.0.0/0
HTTPS       TCP        443          0.0.0.0/0
Custom      TCP        3001         제거 권장 (내부 통신만)
```

**프론트엔드 (Amplify)**:
```
VITE_API_BASE_URL=https://playlist-api.duckdns.org/api/spotify
```

**백엔드 (EC2)**:
```
PORT=3001
NODE_ENV=production
CLIENT_URL=https://main.d2wur1i1ypx7nc.amplifyapp.com
SPOTIFY_CLIENT_ID=075a01b11b724949a4795478af123221
SPOTIFY_CLIENT_SECRET=7f692584fdc84ba6ad83e2649083d6fc
```

**백엔드 HTTPS 엔드포인트**:
```bash

# 정상 응답
```

**프론트엔드 통합 테스트**:
1. https://main.d2wur1i1ypx7nc.amplifyapp.com 접속
2. 검색 기능 테스트 (예: "BTS" 검색)

## 7. 교훈 및 개선 사항

### 배운 점

#### 1. DNS 전파 시간의 중요성
- Let's Encrypt SSL 인증서 발급 실패의 주요 원인
- 도메인 설정 후 충분한 시간(30분~1시간) 기다려야 함
- 성급하게 여러 방법 시도하기보다 시간을 두고 재시도하는 것이 효과적

#### 2. CORS의 정확한 매칭
- Trailing slash(`/`) 하나로 CORS 에러 발생
- Origin 문자열은 정확히 일치해야 함
- 환경변수 설정 시 주의 필요

#### 3. PM2 Working Directory
- `.env` 파일 위치와 PM2의 working directory가 일치해야 함
- PM2 start 시 현재 디렉토리가 중요
- PM2 restart는 기존 설정 유지하므로 위치 무관

#### 4. Nginx 리버스 프록시의 장점
- SSL 종료(SSL Termination)를 Nginx에서 처리
- 백엔드는 HTTP로 실행 가능 (SSL 설정 불필요)
- 포트 80/443만 외부에 노출, 백엔드 포트는 내부 통신만

#### 5. 환경변수와 빌드의 관계
- `.env` 파일 수정: 빌드 불필요, 재시작만 필요
- TypeScript 코드 수정: 빌드 필요, 재시작 필요
- 적절히 구분하면 배포 시간 단축 가능

### 개선 가능한 점

#### 1. 보안 강화
- EC2 보안 그룹에서 3001 포트 규칙 제거 (내부 통신만)
- SSH 포트 변경 (22 → 다른 포트)
- Fail2ban 설치 (무차별 대입 공격 방지)

#### 2. 모니터링 추가
- PM2 모니터링 도구 (PM2 Plus)
- Nginx 로그 분석
- 에러 로깅 시스템 (Sentry 등)

#### 3. CI/CD 파이프라인
- GitHub Actions로 자동 배포
- 테스트 자동화
- 배포 전 자동 빌드 및 검증

#### 4. 도메인 개선
- 무료 도메인(DuckDNS) → 유료 도메인 고려
- Route 53 + CloudFront 조합도 고려

#### 5. 백엔드 확장성
- PM2 Cluster Mode (멀티 코어 활용)
- Load Balancer 추가 (트래픽 증가 시)
- Docker 컨테이너화 (일관된 환경)

#### 6. 환경 분리
- 개발(dev), 스테이징(staging), 프로덕션(production) 환경 분리
- 각 환경별 별도의 .env 파일
- 배포 전 스테이징 환경에서 테스트

## 마무리

이번 배포 과정에서 가장 중요했던 교훈은 **"시스템의 각 계층이 어떻게 상호작용하는지 이해하는 것"**이었습니다.

- 브라우저의 보안 정책 (Mixed Content, CORS)
- DNS의 작동 방식과 전파 시간
- Nginx의 리버스 프록시 역할
- PM2의 프로세스 관리와 working directory
- 환경변수의 적절한 관리

각각의 문제는 단순해 보였지만, 전체 시스템을 이해하지 못하면 해결하기 어려웠습니다.
특히 DNS 전파 시간을 기다리지 않고 여러 방법을 시도하다가 오히려 시간을 낭비한 경험은
"때로는 기다리는 것도 해결책"이라는 교훈을 주었습니다.

이제 안정적으로 배포된 시스템을 바탕으로 더 많은 기능을 개발하고,
사용자 경험을 개선해 나갈 수 있게 되었습니다.
